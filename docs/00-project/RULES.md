# Swag Platform Project Rules

Version: 1.0

Status: Approved

Owner: Project Architect

---

# Purpose

This document defines the official rules of the Swag Platform project.

Every developer, AI coding agent, designer, tester, and future contributor must follow these rules.

Breaking these rules requires approval from the Project Architect.

---

# Rule 1 — Documentation First

Documentation always comes before implementation.

No feature may be developed unless its documentation has been completed and approved.

---

# Rule 2 — Architecture First

Never write code before understanding the architecture.

No developer may change project architecture without updating the documentation.

---

# Rule 3 — One Feature At A Time

Only one feature should be actively developed.

Do not work on multiple unfinished features simultaneously.

Finish one feature before starting another.

---

# Rule 4 — MVP Protection

Version 1 has a fixed scope.

New features must not be added during development unless officially approved.

Ideas should be stored for Version 2.

---

# Rule 5 — Clean Code

Every file must be readable.

Avoid duplicate code.

Create reusable components.

Avoid unnecessary complexity.

Prefer clarity over cleverness.

---

# Rule 6 — UI Consistency

Every screen must follow the Design System.

Do not invent new colors.

Do not invent new spacing.

Do not invent new typography.

Do not create random UI styles.

---

# Rule 7 — UX Consistency

The application should always feel:

Simple

Fast

Predictable

Comfortable

Premium

---

# Rule 8 — Performance First

Every implementation should consider performance.

Avoid unnecessary rebuilds.

Avoid unnecessary network calls.

Avoid unnecessary animations.

---

# Rule 9 — Mobile First

Swag is a mobile-first application.

Every screen must be optimized for phones before tablets or desktop.

---

# Rule 10 — Security

Never expose secrets.

Never hardcode API keys.

Never commit sensitive credentials.

Use environment variables whenever possible.

---

# Rule 11 — Git Rules

Every feature should have meaningful commits.

Commit messages should clearly describe the work completed.

Never commit unfinished experiments.

---

# Rule 12 — Folder Rules

Never create random folders.

Never rename existing folders without approval.

Keep the repository organized.

---

# Rule 13 — AI Rules

AI is an implementation assistant.

AI must:

Read documentation.

Follow documentation.

Never invent features.

Never redesign architecture.

Never modify approved documentation without permission.

---

# Rule 14 — Human Developer Rules

Read before coding.

Ask before changing architecture.

Follow the roadmap.

Respect documentation.

Update checklists after completing tasks.

---

# Rule 15 — Testing Rules

Every completed feature must be tested.

Basic functionality must work before moving to the next feature.

Critical bugs must be fixed before release.

---

# Rule 16 — Review Rules

Every completed task should be reviewed.

Documentation and implementation must match.

If they do not match, documentation must be updated or implementation corrected.

---

# Rule 17 — Project Philosophy

The goal is not to build the biggest application.

The goal is to build the highest quality application.

Quality is always more important than quantity.

---

# Acceptance Criteria

Project rules are documented.

Developers understand responsibilities.

AI behavior is clearly defined.

Development process is protected.
